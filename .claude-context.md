## Descripción del Proyecto

**Alhabla** es una plataforma **SaaS multi-tenant** que ofrece **recepcionistas de voz con IA**
para pequeños negocios en **España**.

- **Qué hace:** cada negocio dispone de uno o más agentes de voz que atienden las llamadas
  entrantes, responden preguntas, consultan el horario del negocio, comprueban disponibilidad
  y reservan citas directamente en el calendario de Google, Outlook o Apple/iCloud del negocio.
  Desde septiembre de 2026 también hablan por WhatsApp con el dueño (avisos y el Gestor, «Tu
  asistente») y con sus clientes.
- **Para quién:** peluquerías, barberías, salones de uñas, centros de estética y clínicas de
  fisioterapia (`businessType`: `peluqueria`, `barberia`, `salon-de-unas`,
  `centro-de-estetica`, `fisioterapia`, `other`).
- **Mercado:** España / Europa. Voz con **Telnyx AI Assistants** (primario) y **Retell.ai**
  de respaldo.
- **Modelo de negocio:** suscripción con Stripe y 7 días de prueba. Planes:
  - `inicio` — 69 €/mes, 100 min incluidos, 0,45 €/min extra
  - `pro` — 149 €/mes, 400 min incluidos, 0,40 €/min extra (destacado)
  - `scale` — 299 €/mes, 1000 min incluidos, 0,35 €/min extra
- **Idioma del código:** **todo el codebase está en español** — copy de UI, comentarios,
  nombres de variables y lógica de negocio. Mantén todo en español al modificar código o
  añadir texto visible para el usuario. El inglés solo se acepta para términos técnicos
  (`routes.ts`, `service.ts`, `prisma`, `fastify`…).

| Capa | Tecnología |
|------|------------|

| Pagos | Stripe (Checkout Sessions embebido, Customer Portal, webhooks) |
| Calendario | Google Calendar API (`googleapis`), Microsoft Graph (Outlook), CalDAV (`tsdav` + `ical.js`, Apple/iCloud) |
| Auth | JWT propio (`jsonwebtoken`, sin `@fastify/jwt`) con `tokenVersion` + Google OAuth 2.0 + `bcryptjs` (coste 12) |
| Validación | Zod 3 |
| Contenedores | Docker + Docker Compose (perfiles `dev` / `prod`) |
| Testing | Vitest 4; los de integración van contra el Postgres/Redis reales de docker-compose (BD `alhabla_test`), sin MSW ni testcontainers |
| Formato / Lint | Prettier (`.prettierrc` de la raíz) + ESLint (`typescript-eslint`, config `recommended`) |

Puertos: backend `3000`, la app (`frontend/`) `3001`, la web pública (`web/`) `3002`, Prisma Studio `5555`. El backend local sale a internet por un túnel con nombre de Cloudflare en `https://dev-api.alhabla.ai` (`BASE_URL`), no por ngrok.

### Frontend

Desde el 2026-09-21 hay dos proyectos Next.js: `frontend/` (la app, `app.alhabla.ai`) y `web/`
(la web pública, `alhabla.ai`: landing, sectores, planes, legal, registro y blog en MDX). Ver
`docs/historico/PLAN-APP-DOMINIO.md`.

| Capa | Tecnología |
|------|------------|
| Framework | **Next.js 14** (App Router), React 18, TypeScript 5 — las dos |
| Styling | **Tailwind CSS v3.4** + variables CSS en el `globals.css` de cada una + PostCSS |
| Estado servidor | TanStack Query v5 (`staleTime: 30s`, sin retry, sin refetch on focus) — solo la app |
| Estado global | `BusinessProvider` (context de la app): `business`, `isLoadingBusiness`, `hasToken`, `isError`, `errorMessage` |
| HTTP | Axios: la app con interceptor de Bearer token; la web sin token (nunca tiene sesión) |
| Iconos | **Lucide React** (+ `@icons-pack/react-simple-icons` para logos de marca) |
| Animación | Framer Motion 10, solo en la web; la app usa Lottie (`lottie-react`) en `/bienvenida` y `/agente` |
| Gráficas | Sin librería: las barras de `/llamadas/analitica` son HTML y Tailwind (Recharts salió en el rediseño de agosto de 2026) |
| Pagos | `@stripe/react-stripe-js` + `@stripe/stripe-js` (Embedded Checkout, en la app) |
| Demo de voz | `POST /demo/web-call` (web pública) — llamada WebRTC de Telnyx (`@telnyx/webrtc`, `anonymous_login`) a un assistant de demo aislado |
| Blog | MDX (`next-mdx-remote` + `gray-matter`) con editor Keystatic (`@keystatic/core`, `@keystatic/next`) — en la web |
| Analítica | GA4 y Vercel Analytics tras la cookie de consentimiento `alhabla_analitica`, la misma en las dos |
| Lint / tests | `eslint-config-next` (`next/core-web-vitals` + `next/typescript`); Vitest + Testing Library + jsdom |

- **Proxy (las dos webs, solo sirve en dev):** `/api/backend/:path*` → `http://localhost:3000/:path*`
  (rewrites en `frontend/next.config.mjs` y `web/next.config.mjs`). En producción apunta a
  localhost y falla: el código llama siempre por el cliente `api` de `lib/api.ts`, y el build de
  producción de cada web se rompe a propósito si falta `NEXT_PUBLIC_API_BASE_URL`.
- **Redirects:** la app manda con 301 las rutas de marketing a la web (`/landing`, sectores,
  `/planes`, `/blog`, `/legal/*`, `/register`), `/register/business/*` → `/bienvenida/*`,
  `/gestor` → `/asistente` y, temporal, `/ajustes/calendario` → `/agente` (botón de las alertas
  de WhatsApp); la web manda con 301 las rutas de la app a `app.alhabla.ai` y los plurales de
  sector (`/peluquerias`…) al singular.
- **Persistencia en cliente:** la app guarda en `localStorage` el token (`alhabla_token`; legacy
  `token`, `jwt`), el plan pendiente (`alhabla_pending_plan`) y el estado del asistente de alta
  (`alhabla_registration_niche`, `alhabla_detected_business_type`, `registration_next_step`); la
  web, la estimación de ROI en `localStorage` y el contexto calculadora → `/planes` en
  `sessionStorage`, con TTL de 1 hora.

> Nota: el `package.json` de la raíz solo declara `playwright` como devDependency (capturas y
> pruebas manuales); no es un workspace. Las dos webs usan **Tailwind 3.4**.

`retellSimulation` no tienen `routes.ts`: los llaman las rutas de webhooks o `scripts/`.

## Constraints & Limitaciones

**Producto y negocio**
- **Orquestador de voz:** `detectVoiceOrchestrator()` sigue devolviendo `retell` en el alta,
  pero con `VOICE_TELNYX_ROLLOUT` activo `createBusinessAgent` promociona el negocio a
  `telnyx` en cuanto existe su assistant: en la práctica todos son Telnyx-primario (ver
  `AGENTS.md` § Orchestrator Field). Un cambio que solo llegue a Retell no llega a ninguna
  llamada real.
- Idioma por defecto del agente `es-ES`, zona horaria `Europe/Madrid`.
- El alta termina en el checkout de Stripe (7 días de prueba), y es **obligatorio**: sin
  suscripción `ACTIVE`/`TRIALING` no se compra número (`POST /phone/business/me/phone/provision`
  responde 402), así que la recepcionista no atiende nada.
- `createCheckoutSession` rechaza si el negocio ya tiene suscripción activa o en trial.

**Límites técnicos duros**
- Rate limiting: 100 req/min global (contador en Redis con `skipOnError: true`) · 300 req/min en
  los webhooks de Retell y Telnyx · en `/auth/*`, 10/min en `/login`, Google y `GET /account`, y
  5/min en `/register`, `/pase/canjear`, recuperación y cambio de contraseña, borrado de cuenta y
  `/register-first-user`, con un techo de respaldo en memoria de 40/min por IP
  (`lib/limitadorEnMemoria.ts`) por si Redis cae · 20/min en los endpoints de Places (también los
  de la demo) · 10/min en `POST /demo/web-call` · `/internal/jobs/*` exentas.
- JWT: expiración de **7 días**. `JWT_SECRET` obligatorio (el servidor no arranca sin él). Lleva
  `tv` (`User.tokenVersion`): cambiar o restablecer la contraseña invalida los tokens anteriores
  (se comprueba contra la BD con caché de 30 s y, si falla, deniega).
- CORS restringido a los orígenes exactos de `origenesPermitidos()` (`backend/src/lib/urls.ts`):
  `APP_URL`, `WEB_URL` y el opcional `EXTRA_ALLOWED_ORIGIN`. `FRONTEND_URL` solo entra como
  respaldo cuando faltan `APP_URL`/`WEB_URL`.
- Duración de servicios: **5–480 minutos**. Capacidad de reserva 1–50. Profesionales activos por
  plan (`lib/planFeatures.ts`): Inicio 3, Pro 10, Scale sin límite; el paso «Equipo» del alta
  ofrece de 1 a 20 (tope solo del formulario).
- Horario: 7 días, máximo **3 intervalos no solapados** por día, formato `HH:mm`, más hasta 120
  excepciones por fecha (`exceptions`: cerrado, o hasta 3 tramos `HH:mm`).
- Clasificación de llamadas (`CallOutcome`): sin LLM propio (se eliminó `classifyCall.ts`/Claude
  Haiku). En Telnyx la ponen los insights de la cuenta (`TELNYX_INSIGHT_*_ID`, evento
  `call.conversation_insights.generated`) y el informe final de la tool `informar_al_negocio`,
  que solo rellena lo que siga en `null`; en Retell, `post_call_analysis_data`.
- Cloud Tasks (reintentos por cola): `process-recording` 5 intentos/backoff 1s ·
  `retry-failed-booking` 4 intentos/backoff 30s · `send-email` 4 intentos/backoff 5s.
- Limpieza de llamadas zombie: cada 15 min, umbral 20 min (el agente cuelga solo a los 10).
- Caché Redis de configs de voz: `voice_config:<businessId>`, TTL 3600s. Tras tocar el
  calendario u otro campo cacheado, invalídala con `invalidarCacheDeVoz()`
  (`lib/voiceConfigCache.ts`).

**Rendimiento**
- TanStack Query (app): `staleTime` 30s, sin reintentos, sin refetch al enfocar. Cualquier vista
  nueva debe respetar esta config en vez de inventar la suya; la única excepción es la consulta
  del negocio de `BusinessProvider` (`my-business`), que sí refresca al enfocar.
- `PATCH /business/me` reescribe el `systemPrompt` de todos los agentes en paralelo
  (`Promise.all`) y, si cambia algo que afecta al prompt, lo empuja a Retell y a Telnyx dentro de
  la misma petición (`syncAgentToRetell` y `syncAgentToTelnyx`, que recorren los agentes uno a
  uno): cada llamada externa suma a la latencia de esa respuesta.
- `UpcomingBookings` (en `PanelInicio`) refresca cada 5 min — no bajes ese intervalo.
- `/health` comprueba Postgres, Redis y, si hay `RETELL_API_KEY`, Retell; `200` si todo sano,
  `503` si degradado. Telnyx no entra: lo vigila el job `telnyx-health-check`.

**Compatibilidad / soporte**
- Móvil: `AppShell` cambia la barra lateral por cabecera y barra de navegación inferior, y las
  landings tienen menú móvil (`MobileNav`). El diseño debe ser responsive.
- La demo de voz requiere permiso de micrófono en el navegador: va por Telnyx WebRTC
  (`@telnyx/webrtc`, `anonymous_login`) desde el 2026-09-22 y necesita un navegador moderno con
  WebRTC.
- Sin objetivo declarado de soporte para navegadores legacy ni Lighthouse: `next/core-web-vitals`
  es el único listón automatizado. **Si necesitas targets numéricos de performance o una
  matriz de navegadores concreta, hay que definirlos — no están en `AGENTS.md`.**

## Lo que NO tocar

**Seguridad — crítico**
- Verificación de firmas de webhooks: firma de Retell (`x-retell-signature`, un único
  `preHandler` en `backend/src/plugins/firmaRetell.ts` para todas las rutas de
  `modules/webhooksRetell/`), firma Ed25519 de Telnyx (un
  único `preHandler` en `backend/src/plugins/firmaTelnyx.ts` para todas las rutas de
  `modules/webhooksTelnyx/`) y firma de Stripe (ruta con `rawBody: true`). No relajes, saltes
  ni "simplifiques" ninguna de estas validaciones.
- **Aislamiento multi-tenant:** toda consulta con ámbito de negocio se filtra por
  `request.user.businessId` tomado del token. **Nunca** aceptes un `businessId` del body para
  lecturas o escrituras.
- `JWT_SECRET` obligatorio y CORS bloqueado a `origenesPermitidos()` (`lib/urls.ts`: `APP_URL`,
  `WEB_URL` y el opcional `EXTRA_ALLOWED_ORIGIN`; `FRONTEND_URL` solo como respaldo). No añadas
  orígenes comodín.
- `rawBody` solo está activado en las rutas de webhook de Retell, Telnyx y Stripe
  (`/billing/webhook`) — no lo extiendas a rutas normales (coste de memoria).
- **Nunca** commitees `.env`. Ojo: en la raíz hay un `.env` con credenciales reales;
  `.gitignore` excluye cualquier `.env*` salvo `.env.example`.

**Arquitectura — respetar los límites**
- **Adaptadores como única fuente de verdad:** Retell pasa por
  `backend/src/adapters/retell/RetellAdapter.ts`; Telnyx por `adapters/telnyx/TelnyxAdapter.ts`
  (números) y `TelnyxAiAdapter.ts` (assistants), y WhatsApp por
  `adapters/whatsapp/WhatsAppAdapter.ts`. Jamás llames a esas APIs directamente desde un route
  handler.
- **Idempotencia de Stripe:** los eventos se deduplican vía la tabla `StripeWebhookEvent`. Los
  fallos de Telnyx durante `provisionPhoneNumber` **no** deben hacer fallar la respuesta del
  webhook de Stripe (ese comportamiento es intencional).
- **Provisioning de teléfono:** `provisionPhoneNumber` corre en `checkout.session.completed` (y,
  de respaldo, al reconciliar el checkout) **esperándolo** con `await`, no en segundo plano: en
  Cloud Run, sin esperarlo, el proceso puede quedarse sin CPU tras responder y dejar la cuenta
  pagada sin número. Nunca lanza (devuelve `{ success: false }`), así que no tumba el webhook.
  Mantén la tolerancia a fallos parciales que ya cubren los tests.
- Los campos `stripeCustomerId`, `stripeSubscriptionId`, `telnyxPhoneNumber`,
  `telnyxPhoneNumberId`, `retellPhoneNumberId` y `retellPhoneNumber` son **únicos** en el schema.
- Las credenciales de calendario **no** viven en `Business`: están en la tabla
  `calendar_connections` (una fila por negocio y proveedor), cifradas en reposo con AES-256-GCM y la
  clave `CALENDAR_CREDENTIALS_KEY`. Las columnas `google*`/`outlook*` de `businesses` se borraron el
  2026-09-18; en `Business` solo queda `calendarProvider` como puntero al proveedor activo. Todo
  acceso pasa por `modules/calendar/conexion.ts` (los demás módulos incluyen la relación con sus
  `SELECT_CONEXION_DE_CALENDARIO`/`INCLUDE_CONEXIONES` y la resuelven con sus funciones), solo ese
  fichero cifra y descifra, y cada proveedor es un adaptador en `adapters/calendar/` (`google`,
  `outlook`, `caldav`). No las muevas ni las expongas por API.
- La completitud de los pasos de onboarding se **calcula en vivo** desde los datos del negocio.
  En `OnboardingState` solo se persisten `dismissedAt`, `completedAt` y lo que no se puede leer
  de otro sitio: `forwardingConfirmedAt` (el dueño dice haber activado el desvío) y
  `forwardingCheckedAt` («Comprobar desvío» lo verificó); la columna `steps` no se escribe. No
  conviertas los pasos en estado persistido.
- El default de `orchestrator` es `retell` por RGPD. No lo cambies a la ligera.

**Convenciones que no se negocian**
- Imports con extensión `.js` en rutas TypeScript (requisito de ESM):
  `import { prisma } from "../../lib/prisma.js";`.
- Prettier: `semi: true`, `trailingComma: "es5"`, `singleQuote: false`, `printWidth: 80`,
  `tabWidth: 2`.
- Alias: backend `"@/*"` → `"./src/*"` (es decir, `backend/src/`); la app y la web,
  `"@/*"` → `"./src/*"`.
- Logs prefijados con el módulo entre corchetes: `[Agent]`, `[Calendar]`, `[Job]`.
  `fastify.log` dentro de rutas; `console.log`/`console.error` en arranque y workers.
- Nueva variable de entorno ⇒ añadirla a `.env.example` **y** a `docker-compose.yml`
  (servicios `backend` y `backend-dev`). Sin defaults reales para secretos.
- El proyecto **sí es un repositorio git** (rama `main`). Hay historial y se puede revertir, pero
  nunca commitees `.env` ni ninguna copia (`.env.bak`, `.env.google`…): están en `.gitignore` por
  algo.

## Audiencia

**Usuario final (cliente de pago):** dueño o gerente de un pequeño negocio de servicios en
España — peluquería, barbería, salón de uñas, centro de estética, clínica de fisioterapia.

- Perfil: no técnico. Trabaja de cara al público y no puede coger el teléfono mientras atiende.
  Suele ser un negocio de 1 a 20 empleados.
- Dolor principal: **llamadas perdidas = citas perdidas = ingresos perdidos**. De ahí que el
  producto lleve calculadora de pérdida de ingresos (`RevenueLossCalculator`) y copy orientado
  a ROI en `/planes`.
- Expectativa: configurarlo una vez y olvidarse. Por eso, tras crear la cuenta en la web, el
  alta en la app es guiada paso a paso (Places → nicho → servicios → equipo → calendario →
  checkout) con plantillas por nicho y la posibilidad de saltarse pasos y completarlos luego en
  `/agente` (la checklist del panel los enlaza).
- Nivel de tolerancia: bajo a la jerga técnica y a la fricción. Nada de terminología de
  "LLM", "orquestador", "webhook" o "API" en la UI.

**Usuario secundario (quien llama):** el cliente del negocio que llama por teléfono y habla con
el agente de voz. Habla español, espera una respuesta natural y rápida, y no debería notar que
está hablando con una IA torpe. El prompt del agente incluye instrucciones explícitas para
**nunca inventar datos** y comprobar siempre con `check_availability` (valida horario,
restricciones, capacidad y calendario, y devuelve el `availabilityToken` que exige
`book_appointment`) antes de reservar; `get_catalog` da los servicios y profesionales reales.
`check_business_hours` ya no existe (borrada el 2026-09-29; ningún agente la registraba desde el 09-09).

## Tono & Voz

**Principio rector:** confianza tranquila y profesional. Alhabla le habla a un negocio
tradicional, no a un early adopter de tecnología.

- **Idioma:** español de España, siempre. Tuteo en la UI del producto.
- **Registro:** cercano pero serio. Ni corporativo acartonado ni startup con emojis.
- **Concreto sobre abstracto:** el copy se apoya en números y resultados verificables — minutos
  incluidos, euros por minuto, citas recuperadas, ROI. Las landings por nicho llevan
  `sectorData` con `stats` (cada cifra con su `source`) y, en algunas, `quotes`, precisamente
  para respaldar las afirmaciones.
- **Enfocado al dolor, sin alarmismo:** cada nicho tiene sus `highlights` y `benefits` con un
  campo `result` explícito, y su `sectorData` puede traer un `painPoint`. Se nombra el problema y
  se cuantifica la solución; no se exagera.
- **Sin jerga de IA:** hablar de "recepcionista virtual" y "agente de voz", no de modelos,
  prompts ni orquestadores. El usuario compra una recepcionista, no una IA.
- **Voz del agente telefónico:** cálida y eficiente. Mensaje inicial por defecto:
  *"Hola, soy la recepcionista virtual. ¿En qué te ayudo?"*. El tono es configurable por negocio
  en `AgentSettingsEditor`:
  - **Tono:** `warm` / `professional` / `direct`
  - **Objetivo:** `bookings` / `customer_service` / `lead_capture`
  - **Estilo de respuesta:** `concise` / `balanced`
  - **Escalado:** `take_message` / `request_callback`
- **Personalización por nicho:** títulos, subtítulos y CTAs cambian según `businessType` vía
  `BUSINESS_TYPE_ONBOARDING_TEXTS` (`frontend/src/lib/business-type.ts`, en los pasos de
  `/bienvenida`). Una peluquería y una clínica de fisioterapia no leen el mismo copy.
- **Errores:** mensajes en español, accionables y sin culpar al usuario. Los errores 5xx del
  backend devuelven un genérico ("Internal server error") para no filtrar internals — la UI debe
  traducir eso a algo humano. Ojo: `describeApiError` (`frontend/src/lib/api-errors.ts`) enseña
  el `error` del cuerpo si es corto, y el de muchos 500 está en inglés («Internal Server Error»,
  «Failed to update business»), así que hoy puede llegar tal cual a pantalla.
